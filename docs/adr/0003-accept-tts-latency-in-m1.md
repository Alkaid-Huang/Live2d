# 0003. M1 接受云端 TTS 的首音延迟，串行合成推迟到 M2

- 日期：2026-09-21
- 状态：已采纳

## 背景

M1 收尾时用 `tests/probe_turn.py --turns 3` 真实跑了一轮链路（DeepSeek + edge-tts）：

| 轮次 | 首字 | 首音 | 整轮 |
|---|---|---|---|
| 1（进程冷启动） | 4000ms | 7563ms | 12984ms |
| 2 | 704ms | 6907ms | 6907ms |
| 3 | 1015ms | 5187ms | 5187ms |

再单独量 edge-tts（同一句话合成三次）：16.6 秒（含首次握手）、2.8 秒、4.7 秒。

结论：首字达标（US-1 要 < 3 秒，稳态 0.7–1.0 秒），**首音不达标**（US-2 原定 < 2.5 秒）。
两个独立的原因：

1. **TTS 单次调用本身就是 3–5 秒。** 云端服务的网络往返成本，与代码怎么写无关。
2. **LLM 与 TTS 串行。** `runtime` 先把整段回复流完，才切句送去合成，所以首音 =
   整段回复的生成时间 + 一次 TTS 的时间。参照项目按句边流边合成，正是为了避开这一项。

## 决定

1. **把 US-2 的验收标准从 2.5 秒改成 8 秒（P95）**，并在 `docs/product.md` 里写清原因。
2. **不改打点口径。** 界面打的是"按下发送 → 第一片音频"，那正是用户能感知的延迟；
   "回复生成完毕 → 首音"是内部衔接开销，留在需要时再加，不作为验收标准。
3. **边流边合成不在 M1 做**，排到 M2 第一项。

## 理由

1. M1 的目标是把链路跑通、并且让它可测，不是调延迟。为了 2.5 秒去改核心层的执行顺序，
   会连带改事件契约、改事件顺序，把 M1 的收尾拖长。
2. "实测 5–8 秒、原因是云端 TTS 的单次往返、方案是先并行再换后端"本身就是一份完整的
   工程判断，比硬凑一个达标数字更能说明问题。
3. 反过来，如果标准留在 2.5 秒而实际做不到，M1 就只能算没完成——那是把文档写成愿望，
   不是把文档写成契约。

## 代价

- M1 的首音比理想慢 5 秒左右：按下发送之后要等一下才听见声音。界面从第一天就有
  "合成语音…"状态，所以这一段等待不是空白的（见 docs/contracts.md 第 2 节）。
- 8 秒是 P95 口径，单轮实测最快 5.2 秒；上面的数字来自开发机，且经过了开发环境的网络，
  换机器复测请用 `run.bat`，并把结果记进 `docs/smoke-test.md` 的延迟表。

## 什么时候把 M2 的第一项提前

满足任意一条：

- 首音稳定超过 10 秒，或出现明显限流
- 演示需要连续多轮对话，等待感成为主要问题

至于要不要**换掉** edge-tts（本地模型能把单次合成压到毫秒级，代价是几 GB 模型和显存），
触发条件写在 ADR 0001。
