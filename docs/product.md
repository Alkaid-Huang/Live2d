# 产品定义

## 这是什么

一个跑在你自己电脑上的 Live2D 数字角色：你打字，它用大模型回复，用语音说出来，脸上有表情、嘴跟着声音动。

求职作品。目标岗位是 AI Agent / LLM 应用工程师，所以这个项目要证明的不是"我会做 Live2D"，而是：能划清多模块系统的边界、能接多家 LLM 并统一路由、能把流式链路（LLM → TTS → 动画）编排正确、能让这些都可测试。

## 参照项目与差异

架构思路参照 [D_sakiko](https://github.com/MacchaPafe/D_sakiko)。差异：

| 项目 | 参照项目 | 本项目 M1 |
|---|---|---|
| 语音输入（ASR） | 有 | **砍掉**，输入只有文本 |
| 语音合成 | 本地 GPT-SoVITS，可克隆音色 | edge-tts（在线），理由见 ADR 0001 |
| 运行形态 | 桌面多进程，后期加了 WebUI | 先桌面多进程，预留 Web 接缝，见 ADR 0002 |
| 情感判断 | 自训练的七分类模型 | 关键词规则 |
| ReAct / RAG / 长期记忆 | 有 | **不做** |
| 分发 | 打包exe + 自动更新 + 修复器 | 本机脚本，不做打包 |

## 用户

会用命令行、能自己填 API Key 的开发者或二次元爱好者。不是普通消费者。

这一点很重要：它决定了 M1 不需要图形化配置界面、不需要安装包、不需要自动更新——配置只走 `.env` 就够。

## 痛点（相对自己拼装）

- 现成的 VTuber 工具偏直播推流，Agent 能力弱
- 自己拼 LLM + TTS + Live2D，三部分接口各不相同，拼起来难测、难换
- 换一家 LLM 供应商就要改代码

## 价值主张

- **可换 Provider**：改 `.env` 就能换 LLM，不用动代码
- **链路完整**：文本 → 回复 → 语音 → 表情口型，一条链真正跑通
- **可测试**：LLM 与 TTS 都能在测试里 mock，不联网也能跑 CI
- **可替换**：TTS 是可插拔的后端，以后换本地模型不重写上层

**不要这么写**："数据不上传、完全本地"。M1 的语音走微软的在线服务，这句站不住（见 ADR 0001）。说"LLM 可接本地模型"是成立的，说"数据不出本机"不是。

## M1 范围

做：

- 文本输入 → LLM 流式回复 → TTS → Live2D 表情 + 口型
- LLM 路由支持两个 Provider（DeepSeek + 一个 OpenAI 兼容端点）
- 情感用关键词规则，不上模型
- 每个模块有单元测试，CI 跑 lint + 类型检查 + 测试
- 本机一键启动脚本
- README + 架构说明

不做：见文末「故意不做」。

## 用户故事与验收标准

**US-1 文本对话**
我输入文本后能看到角色逐字回复。
验收：首字延迟 P95 < 3 秒；流式逐字显示；回复符合角色人设。

**US-2 语音**
我能听到角色用指定音色说话。
验收：从回复生成完毕到第一段音频就绪 < 2.5 秒；音频清晰无杂音；新消息进来时旧语音立刻停止。

**US-3 Live2D 表现**
我看到角色有表情和口型。
验收：模型正常加载且待机动作循环；说话时口型跟随音量；按情感切换 2–3 种表情或动作。

**US-4 LLM 切换**
我改配置就能换 LLM。
验收：改 `.env` 里的 Provider 和模型名，重启后生效；两个 Provider 都能正常对话；不填 Key 时给出明确报错而不是崩。

## 成功指标

- 首字延迟 P95 < 3 秒
- 首音延迟 P95 < 2.5 秒
- 核心层（`runtime` / `llm` / `tts` / `emotion` / `config`）行覆盖率 ≥ 80%；界面与渲染进程不计入
- 本机一键启动连续 5 次成功

延迟数据怎么来：跑 M1-6 的冒烟清单时手记，攒够样本再算 P95。不为了凑数据去写压测框架。

## M1 任务切分

| 编号 | 任务 | 产出 |
|---|---|---|
| M1-1 | 项目骨架 + LLM 路由层 | `pyproject.toml`、`.env.example`、`.gitignore`、`ci.yml`、`config.py`、`llm/`、测试 |
| M1-2 | TTS 抽象接口 + edge 实现 | `tts/base.py`、`tts/edge_impl.py`、测试（全 mock） |
| M1-3 | 情感规则与映射表 | `emotion/rules.py`、`emotion/mapping.py`、测试 |
| M1-4 | 事件与运行时 | `events.py`、`runtime.py`、测试 |
| M1-5 | Live2D 渲染子进程 | `live2d/renderer.py`（含音量驱动口型） |
| M1-6 | 界面装配 + 一键启动 + 冒烟 | `ui/window.py`、`main.py`、`run.bat`、冒烟清单、README 补完 |

规则：一次只做一个，做完提交、开新会话再做下一个。

## 路线图

- **M1 闭环**（本次）
- **M2 表现力**：情感换成分类模型、多角色、会话持久化、动作与表情更丰富
- **M3 能力**：ReAct 工具调用 + RAG 知识库
- **M4 材料**：性能数据、演示与答辩稿

## 故意不做

这些不是遗漏，是明确决定不做。实现时不要顺手补上：

- 语音识别（ASR）
- ReAct 引擎、工具调用、自纠错
- RAG、向量数据库
- 长期记忆与反思机制
- 情感模型微调
- Docker 与容器化（见 ADR 0002）
- 打包成 exe / 安装包、自动更新器、修复器
- 图形化配置界面（配置只走 `.env`）
- 直播推流、多用户、移动端
- 监控平台、SLO/SLA、灰度发布、值班（单人项目，这些只会变成没人看的半成品）

## 技术风险

按"最可能卡住"排序：

1. **live2d-py 是最大的不确定性。** 它把 Python 版本绑在 3.11，Windows 与 macOS 的 wheel 不一样，上游维护状态不稳定，参照项目甚至自己 fork 了一份来编译。
   **降级方案**：如果卡住超过半天，先用一张静态立绘 + 占位口型跑通整条链路，别让 M1 卡在渲染上。渲染是可以后补的，链路不能。
2. **路径含中文或空格会导致模型加载失败。** 项目路径、模型路径都要检查。
3. **Live2D 模型素材的授权。** 求职展示要注意版权，优先用官方允许使用的样例模型。
4. **edge-tts 依赖网络。** 可能被限流或不可用，音色固定、音质一般。换后端的触发条件写在 ADR 0001。
5. **Windows 下的多进程退出清理。** 子进程没收干净会留僵尸进程，或者出现窗口关不掉。
6. **界面和渲染测不了。** CI 只跑核心层，这两块只能本地冒烟（见 M1-6）。

## 不做的承诺

不承诺数据不出本机（语音走在线服务）；不承诺跨平台（M1 只保证 Windows）；不承诺音质。
