# 产品定义

## 这是什么

一个跑在你自己电脑上的 Live2D 数字角色：你打字，它用大模型回复，用语音说出来，脸上有表情、嘴跟着声音动。

求职作品。目标岗位是 AI Agent / LLM 应用工程师，所以这个项目要证明的不是"我会做 Live2D"，而是：能划清多模块系统的边界、能接多家 LLM 并统一路由、能把流式链路（LLM → TTS → 动画）编排正确、能让这些都可测试。

## 参照项目与差异

架构思路参照 [D_sakiko](https://github.com/MacchaPafe/D_sakiko)。差异：

| 项目 | 参照项目 | 本项目 M1 |
|---|---|---|
| 语音输入（ASR） | 有 | **砍掉**，输入只有文本 |
| 语音合成 | 本地 GPT-SoVITS，可克隆音色 | edge-tts（在线），理由见 ADR 0001 |
| 运行形态 | 桌面多进程，后期加了 WebUI | 先桌面多进程，预留 Web 接缝，见 ADR 0002 |
| 情感判断 | 自训练的七分类模型 | 关键词规则 |
| ReAct / RAG / 长期记忆 | 有 | **不做** |
| 分发 | 打包exe + 自动更新 + 修复器 | 本机脚本，不做打包 |

## 用户

会用命令行、能自己填 API Key 的开发者或二次元爱好者。不是普通消费者。

这一点很重要：它决定了 M1 不需要图形化配置界面、不需要安装包、不需要自动更新——配置只走 `.env` 就够。

## 痛点（相对自己拼装）

- 现成的 VTuber 工具偏直播推流，Agent 能力弱
- 自己拼 LLM + TTS + Live2D，三部分接口各不相同，拼起来难测、难换
- 换一家 LLM 供应商就要改代码

## 价值主张

- **可换 Provider**：改 `.env` 就能换 LLM，不用动代码
- **链路完整**：文本 → 回复 → 语音 → 表情口型，一条链真正跑通
- **可测试**：LLM 与 TTS 都能在测试里 mock，不联网也能跑 CI
- **可替换**：TTS 是可插拔的后端，以后换本地模型不重写上层

**不要这么写**："数据不上传、完全本地"。M1 的语音走微软的在线服务，这句站不住（见 ADR 0001）。说"LLM 可接本地模型"是成立的，说"数据不出本机"不是。

## M1 范围

做：

- 文本输入 → LLM 流式回复 → TTS → Live2D 表情 + 口型
- LLM 路由支持两个 Provider（DeepSeek + 一个 OpenAI 兼容端点）
- 情感用关键词规则，不上模型
- 每个模块有单元测试，CI 跑 lint + 类型检查 + 测试
- 本机一键启动脚本
- README + 架构说明

不做：见文末「故意不做」。

## 用户故事与验收标准

**US-1 文本对话**
我输入文本后能看到角色逐字回复。
验收：首字延迟 P95 < 3 秒；流式逐字显示；回复符合角色人设。

**US-2 语音**
我能听到角色用指定音色说话。
验收：从按下发送到听见第一句语音 < 8 秒（P95）；音频清晰无杂音；新消息进来时旧语音立刻停止。

为什么是 8 秒而不是更小：语音走云端服务，**单次合成就要 3–5 秒**的网络往返，而 M1 是等 LLM
把整段回复说完才开始合成（串行）。改成"边流边按句合成"能省 1–2 秒，但它会改变事件顺序
（`tts.chunk` 跑到 `llm.done` 之前），要先改 `docs/contracts.md`，所以排到 M2 第一项。
实测数据与决策见 ADR 0003。

**US-3 Live2D 表现**
我看到角色有表情和口型。
验收：模型正常加载且待机动作循环；说话时口型跟随音量；按情感切换 2–3 种表情或动作。

**US-4 LLM 切换**
我改配置就能换 LLM。
验收：改 `.env` 里的 Provider 和模型名，重启后生效；两个 Provider 都能正常对话；不填 Key 时给出明确报错而不是崩。

## 成功指标

- 首字延迟 P95 < 3 秒
  （实测：稳态 0.7–1.0 秒；进程冷启动那一轮约 4 秒，含 `import litellm` 的 3.4 秒，预热排在 M2）
- 首音延迟 P95 < 8 秒
  （实测 5.2–7.6 秒。原定 2.5 秒，改到 8 秒的原因见 ADR 0003）
- 行覆盖率 ≥ 80%，口径：`src/` 下除三个薄壳外全部计入（`main.py`、`ui/window.py`、
  `stage/renderer.py` 不计，理由见 ADR 0002）
- 本机一键启动连续 5 次成功

延迟数据怎么来：跑 M1-6 的冒烟清单时手记，攒够样本再算 P95。不为了凑数据去写压测框架。

## M1 任务切分

| 编号 | 任务 | 产出 |
|---|---|---|
| M1-1 | 项目骨架 + LLM 路由层 | `pyproject.toml`、`.env.example`、`.gitignore`、`ci.yml`、`config.py`、`llm/`、测试 |
| M1-2 | TTS 抽象接口 + edge 实现 | `tts/base.py`、`tts/edge_impl.py`、测试（全 mock） |
| M1-3 | 情感规则与映射表 | `emotion/rules.py`、`emotion/mapping.py`、测试 |
| M1-4 | 事件与运行时 | `events.py`、`runtime.py`、测试 |
| M1-5 | 舞台层与渲染子进程 | `stage/` 下 7 个文件：协议、通道、待播队列、口型、情感映射、模型路径、渲染入口 |
| M1-6 | 界面装配 + 一键启动 + 冒烟 | `ui/window.py`、`main.py`、`run.bat`、冒烟清单、README 补完 |

规则：一次只做一个，做完提交、开新会话再做下一个。

## 路线图

- **M1 闭环**（本次）
- **M2 表现力与延迟**，按优先级：
  1. **边流边合成**：LLM 一边出字一边按句送去合成，不再等整段回复说完，首音预计省 1–2 秒。
     **先改 `docs/contracts.md` 第 3 节的事件顺序，再改 `runtime.py`。**
  2. **启动时预热 `import litellm`**：冷启动那一轮的首字从约 4 秒降到 1 秒左右，装配层几行就够。
  3. 情感换成分类模型，并解决 `Hiyori` 这类没有动作组和表情文件的模型看不出情感差异的问题。
  4. 多角色、会话持久化、动作与表情更丰富。
- **M3 能力**：ReAct 工具调用 + RAG 知识库
- **M4 材料**：性能数据、演示与答辩稿

## 故意不做

这些不是遗漏，是明确决定不做。实现时不要顺手补上：

- 语音识别（ASR）
- ReAct 引擎、工具调用、自纠错
- RAG、向量数据库
- 长期记忆与反思机制
- 情感模型微调
- Docker 与容器化（见 ADR 0002）
- 打包成 exe / 安装包、自动更新器、修复器
- 图形化配置界面（配置只走 `.env`）
- 直播推流、多用户、移动端
- 监控平台、SLO/SLA、灰度发布、值班（单人项目，这些只会变成没人看的半成品）

## 技术风险

按"最可能卡住"排序：

1. **live2d-py 的依赖风险已经核实过了**：PyPI 上有 `cp311-win_amd64` 的预编译 wheel，本项目环境（Python 3.11.9 + Windows）可直接安装，不需要像参照项目那样自己编译。但它不是 abi3，**Python 版本必须钉在 3.11**，升到 3.12 就没有 wheel 了。
   **仍然保留降级方案**：如果渲染本身卡住超过半天，先用一张静态立绘 + 占位口型跑通整条链路。渲染是可以后补的，链路不能。
2. **路径含中文或空格会导致模型加载失败。** 项目路径、模型路径都要检查。
3. **模型素材：M1-5 阶段手上还没有。** live2d-py 本身不带模型，必须自己准备。合法来源是 Live2D 官方的**免费素材**：`Hiyori`、`Haru`、`Mao`、`Mark`、`Natori`、`Ren`、`Rice`、`Wanko` 这八个样例模型，许可方式是 Free Material License + 每个模型各自的 Sample Model Terms。两条取用路径：
   - 官方 Cubism Web Samples 仓库的 `Samples/Resources/<模型名>/`（拿 `Hiyori` 举例：目录里是 `Hiyori.model3.json` / `Hiyori.moc3` / `Hiyori.physics3.json` / `motions/`），整个目录解压到 `models/hiyori/` 即可，配置默认值正好指向这里；
   - 官网 Sample Data 下载页（需要先同意前述两份条款）。
   注意：**素材不进 git**（`.gitignore` 已排除 `models/`），换机器要重新放。用于求职展示属于学习和 SDK 集成测试用途；将来若商用，要重新核对条款。

   **M1-6 补充（已核实）**：`Hiyori` 只有 `Idle` 与 `TapBody` 两个动作组，也没有表情文件。所以
   `stage/cues.py` 对任何情感都会回落到待机动作，**US-3 的"按情感切换 2–3 种表情或动作"用这份
   素材验不出来**。这不是装配错误，是素材能力不足；出路见 `docs/smoke-test.md` 的「已知限制」。
4. **edge-tts 依赖网络。** 可能被限流或不可用，音色固定、音质一般。换后端的触发条件写在 ADR 0001。
5. **Windows 下的多进程退出清理。** 子进程没收干净会留僵尸进程，或者出现窗口关不掉。
6. **界面和渲染测不了。** CI 只跑核心层，这两块只能本地冒烟（见 M1-6）。

## 不做的承诺

不承诺数据不出本机（语音走在线服务）；不承诺跨平台（M1 只保证 Windows）；不承诺音质。
