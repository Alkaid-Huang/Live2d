# 技术决策记录

这份文档记录 M1 的技术选择：为什么这么定、代价是什么、什么条件下该推翻；它不写操作步骤（见 [`runbook.md`](runbook.md)），也不列接口签名（见 [`reference.md`](reference.md)）。

原先三份 ADR（0001–0003）的内容合并到这里：后端选型与口型驱动对应第 1、4 条，桌面形态对应第 2 条，首音延迟对应第 3 条。第 5–7 条原先散在代码注释与其它文档里，这次一并收进来。

每一条都按同样的五段写，方便横向对比：**背景**、**决定**、**理由**、**代价**、**什么时候推翻**。

## 1. 语音后端用在线 edge-tts，不用本地 GPT-SoVITS

**背景**
语音合成有两条路。edge-tts 是微软在线服务的封装：调用简单、没有模型加载、不吃 GPU，代价是依赖网络、音色只能从预设里挑、音质一般。本地 GPT-SoVITS 这类方案能克隆任意音色、离线可用，代价是几 GB 模型、首次出声要等模型加载（可能几十秒）、显存约 6G（参照项目 README 的数字）。

**决定**
M1 用 edge-tts，但把 TTS 做成可替换的后端：`TtsBackend` 协议放在 `contracts`，`create_tts_backend()` 是唯一选择实现的地方，只有 `tts/edge_impl.py` 允许 import `edge_tts`。edge 专属参数（音色、语速）走 `TTS_EDGE_` 前缀，合成结果统一是落盘的分片（路径 + 格式 + 序号），不是音频流。

**理由**
1. M1 要证明的是链路编排和可测试性，不是音质。edge-tts 让"语音"这一环第一天就能跑。
2. 求职作品得在别人的电脑上装得起来。要求面试官准备 6G 显存、下几 GB 模型，等于把演示门槛变成筛选门槛。
3. 抽象成本低：一个 Protocol、一个工厂函数、一层异常翻译（`TtsError`），大约一天；换后端时上层一行不改。
4. 后端产文件而不是流，是因为本地模型天然产文件，edge 存成文件只是适配器里几行；统一成分片后，播放、口型、清理都只有一种形状。

**代价**
- 依赖网络：离线用不了，可能被限流；文本会发给微软的在线服务，所以产品文案不能写"数据不出本机"。
- 音色固定，不能克隆成自己的角色；音质上限就是预设音色的水平。
- 提前抽象的那一天在 M1 期间没有直接回报。

**什么时候推翻**
满足任意两条就换：需要专属音色、需要无网络演示、网络延迟或限流成为实际困扰。换的时候写一个新的 `TtsBackend` 实现并在工厂里登记，不改 [`reference.md`](reference.md) 定义的数据形状；如果发现非改契约不可，说明协议抽象漏了什么，先修协议再换后端。

## 2. 桌面优先：单机多进程，不用 Docker，不做打包

**背景**
参照项目先做桌面程序（PyQt5 主进程 + 渲染子进程 + 队列通信），后来才加 WebUI。桌面 GUI 和 Docker 天然冲突：容器里跑起来的窗口没法显示给用户。打包成 exe + 安装包 + 自动更新是另一条成本线，参照项目为此维护了修复器。

**决定**
M1 只做桌面形态：PyQt5 窗口在主进程，渲染跑在 `spawn` 出来的子进程，两个 `multiprocessing.Queue` 传普通字典。不引入 Docker，M1 不写任何 HTTP 代码，也不做 exe 或安装包。核心层（`runtime`、`llm`、`tts/base`、`emotion`、`stage` 的非渲染部分）不 import GUI，为将来的 Web 形态留接缝。

**理由**
1. 打断和口型在本地最省事：取消一个回合就是置标志、调 `tts.cancel()`、往命令队列放一条 `stop_audio`。换成 HTTP 要处理连接断开、任务取消、已经推出去的帧怎么收尾。
2. 音频不用服务化：两个进程传文件路径就够了，不需要音频端点、鉴权、跨设备传输。
3. Docker 在这里帮不上忙：容器里没有可显示的窗口，参照项目的一键启动也是本机程序加脚本，不是容器。
4. 成本能算出来：`pyproject.toml` 把 GUI 依赖单独放进 `[gui]`，CI 只装 `[dev]`；覆盖率排除项只有 `main.py`、`ui/window.py`、`stage/renderer.py` 三个薄壳。这让 CI 在没显示器的机器上仍能跑 lint、类型检查和单测。

**代价**
- 暂时不能从手机或另一台电脑访问。
- CI 覆盖不到界面和渲染，只能靠 `runbook.md` 的 12 项人工清单兜底。
- 多进程的退出清理要自己写：Windows 下 `spawn` 的子进程没收干净会留僵尸进程；渲染进程只在启动 2 秒后检查一次存活，之后崩了没人知道。
- 三个薄壳被排除在覆盖率之外，判断逻辑只能放进 `ui/state.py` 和 `stage/` 的其他模块，往薄壳里堆代码会直接拉低可测比例。

**什么时候推翻**
M1 闭环稳定之后，如果要远程访问或做网页演示，在核心层外面加 FastAPI + WebSocket，把 `Event.to_frame()` 直接当帧发，`RendererControl` 换一个往 WebSocket 写帧的实现，`runtime` 不用改（见 [`architecture.md`](architecture.md) 第 5.4 节）。打包则等到需要交给不用命令行的用户时再做，在那之前 `.env` + `run.bat` 就够。

## 3. 接受云端 TTS 的首音延迟，串行合成推迟到 M2

**背景**
M1 收尾时用 `tests/probe_turn.py --turns 3` 真实跑了一轮（DeepSeek + edge-tts）：

| 轮次 | 首字 | 首音 | 整轮 |
|---|---|---|---|
| 1（进程冷启动） | 4000ms | 7563ms | 12984ms |
| 2 | 704ms | 6907ms | 6907ms |
| 3 | 1015ms | 5187ms | 5187ms |

单独量 edge-tts 同一句话三次：16.6 秒（含首次握手）、2.8 秒、4.7 秒。首字达标（US-1 要求 P95 < 3 秒，稳态 0.7–1.0 秒），首音对不上原定的 2.5 秒。原因有两个且互相独立：TTS 单次调用本身 3–5 秒；LLM 与 TTS 串行，首音 = 整段回复生成时间 + 一次合成。

**决定**
US-2 的验收标准从 2.5 秒改成 8 秒（P95），理由记在本条的「理由」里。打点口径不变，仍是"按下发送 → 第一片音频就绪"。边流边合成不在 M1 做，排在 M2 第一项。

**理由**
1. M1 的目标是跑通并让它可测，不是调延迟。为了 2.5 秒改执行顺序，会连带改事件顺序（`tts.chunk` 跑到 `llm.done` 之前）、改契约、改 `runtime`，把收尾拖长。
2. "实测 5–8 秒、原因是云端往返、方案是先并行再换后端"本身就是完整的工程判断，比硬凑一个达标数字更能说明问题。
3. 8 秒不是随手写的：实测最慢 7.6 秒（冷启动那一轮），留了余量；如果按稳态 5.2–6.9 秒定，冷启动那轮会一直踩线。
4. 标准留在 2.5 秒而实际做不到，M1 就只能记成未完成；文档写成愿望，验收就失去意义。

**代价**
- 按下发送之后要等 5 秒左右才听见声音；界面从第一天就有"合成语音…"状态，这段等待不是空白。
- 8 秒是 P95 口径，单轮最快 5.2 秒；数字来自开发机和开发环境的网络，换机器要用 `run.bat` 复测并更新本条的实测表。
- 串行还会放大整轮时间：分 2 片那一轮整轮 12984ms，其中合成占了两段。
- 冷启动的 4000ms 首字里有 3.4 秒花在 `import litellm` 上，这一轮首音被顶到 7563ms；预热排在 M2。

**什么时候推翻**
首音稳定超过 10 秒，或者出现明显限流；演示需要连续多轮对话、等待感成为主要问题。两条满足任意一条就把 M2 第一项提前：先改 [`architecture.md`](architecture.md) 第 2 节的事件顺序，再改 `runtime.py`。是否换掉 edge-tts 是另一个决定，触发条件在第 1 条。

## 4. 口型只用音频音量驱动，不用 edge 的逐字时间戳

**背景**
edge-tts 能给出逐字（word boundary）时间戳，本地模型给不了。接上时间戳，口型看起来能"对上字"，但这份能力绑在 edge 上。播放发生在渲染子进程：主进程发完 `turn.done` 时音频可能还没开始播（`turn.done` 只代表派发完毕），队列里还压着待播分片。

**决定**
口型只由播放中的音频音量驱动。`stage/renderer.py` 把 mixer 的 PCM 缓冲（16 位有符号、小端、交错声道）交给 `stage/lipsync.py`：按 50ms 一窗算 RMS，低于峰值 8% 算静音，开方（指数 0.5）压缩动态范围，张嘴每秒 18、闭嘴每秒 9。整条链路不读任何时间戳。

**理由**
1. 时间戳是 edge 独有的，换后端就得重写口型；音量对任何音频都成立，换后端只影响 `tts/`。
2. 时间戳给的是"第几个字在什么时刻"，给不出"嘴张多大"；真要用它，还得再维护一张字 → 幅度的表，等于多一份 edge 专属数据。
3. 播放是唯一知道"现在到底有没有声音"的地方。音频进队列、切分片、系统 mixer 的缓冲都会让实际出声晚于派发，合成侧的时间戳对不上播放侧的时刻；音量在播放侧直接采样，没有这个错位。
4. 可测：`compute_envelope` 和 `mouth_value` 的输入是 PCM 字节，测试喂合成波形即可，不需要声卡和窗口。

**代价**
- 口型对不上音素：张大嘴的 /a/ 和扁嘴的 /i/ 在音量上可能一样，画面只有开合，没有元音形状。
- 音量不等于语音：气声、齿音、爆破音都可能让嘴动得不自然；8% 静音门限、0.5 曲线、18/9 的速率、增益都是按观感手调的，换音色或换模型要重调。
- 不支持"先算好整段口型再播"的做法，口型只能跟着播放进度实时算。

**什么时候推翻**
需要音素级口型（比如按元音切换 `ParamMouthForm`）时，音量不够用。那时给 `stage/lipsync.py` 加第二条输入：一个可选的"时间 → 幅度"曲线，由后端提供或离线分析生成；音量路径保留为默认，保证没有时间戳的后端仍能用。只有所有候选后端都能提供对齐数据时，才考虑把音量路径换掉。

## 5. 舞台层叫 stage，不叫 live2d

**背景**
第三方库 live2d-py 提供的顶层模块就叫 `live2d`，用法是 `import live2d.v3`。本项目的包根是 `src/`（`package-dir = {"" = "src"}`，pytest 也把 `src` 放进 `pythonpath`），如果这里再放一个 `src/live2d/`，`import live2d.v3` 会先命中项目自己的包。模块只会加载一次，谁先被 import 谁占住这个名字，之后第三方库再也导不进来，报错还是看不出原因的 `module 'live2d' has no attribute 'v3'`。

**决定**
这一层叫 `stage`。`stage/renderer.py` 是唯一允许 import `pygame` / `live2d` / `OpenGL` / `glfw` 的文件，`stage/__init__.py` 不 import 这些库，渲染进程由 `run_renderer_process()` 在子进程里惰性导入。边界由 `tests/test_layer_boundaries.py` 用 AST 自动检查。

**理由**
1. 冲突无法回避：项目既要用 live2d 库，又想叫 live2d 包，两个名字只能活一个；第三方包名改不了，能改的只有自己这边。
2. `stage` 描述的职责比库名宽：这一层除了画脸，还有命令协议、待播队列、口型计算、情感映射、模型路径解析，换渲染库之后这些仍然存在。
3. 包名和库名分开后，`import live2d.v3` 只出现在 `renderer.py` 一处，`grep live2d` 的结果就是第三方调用点，排查依赖问题时不会混进项目自己的模块。
4. 惰性导入还有一个直接好处：CI 不装 `[gui]`，但 `import stage.protocol`、`import stage.lipsync` 仍能跑，协议和口型才有测试。

**代价**
- 词汇和领域不一致：Live2D 开发者第一反应是找 `live2d/` 目录，得先读 [`architecture.md`](architecture.md) 的用词表。
- `stage` 是个普通英文词，搜索时容易命中无关内容，名字本身不带技术信息。
- 新增模块时如果顺手 import 了 pygame 或 live2d，CI 会失败；提示是清楚的，但要改的是那个文件而不是测试。

**什么时候推翻**
基本不用。只有当渲染技术整体换掉（不再用 live2d-py），并且这一层同时承担多个渲染后端时，`stage` 这个名字才需要重新考虑（比如 `presentation`）。仅仅因为"想和库同名"而改回去，会重新引入同一个 import 冲突。

## 6. 契约集中在 src/contracts/，实现层只依赖契约

**背景**
重构前，契约散在实现层：事件定义在 `src/events.py`，LLM 的消息类型在 `llm/schemas.py`，`TtsBackend` 和 `RendererControl` 分别定义在 `tts/base.py` 与 `runtime.py`。后果是 import 一个类型经常顺带拉进一层实现：界面为了拿事件类型要碰 `events`，测试为了造消息要碰 `llm.schemas`，`stage/protocol.py` 里的 `Message` 与对话 `Message` 还同名不同义。这次重构把端口、事件、数据类型、异常统一搬进 `src/contracts/`。

**决定**
`contracts` 是唯一允许被任何层 import 的包，它自己只 import 标准库和 `contracts` 内部模块。`llm` / `tts` / `stage` / `ui` / `runtime` 都依赖它，依赖方向永远指向 `contracts`。实现细节留在各层：`tts/base.py` 只做 re-export 和切句工具，`llm/router.py` 提供 `RouterLlmClient`，`stage/channel.py` 实现 `RendererControl`。

**理由**
1. 将来接 Agent 工具调用时，变的是 `contracts`（新增 `tool.call` / `tool.result` 之类事件、扩展 `LlmClient`）和 `runtime` 的循环；界面按事件类型渲染，装配层按事件类型分发，不用重新认识 `llm` 或 `tts` 的内部类型。`ui/state.py` 现在就是逐个映射事件，新增一种事件只加一条分支。
2. 异常也收进契约：`LLMError` / `TtsError` 带 `code` 类属性，`runtime` 直接把它写进 `ErrorEvent.code`，不需要 import LiteLLM 或 edge-tts 的异常。换 Provider 或换语音后端，上层捕获的类不变。
3. 契约类型只承载数据：`Message`、`TtsChunk`、`VoiceProfile` 都是 frozen + slots 的 dataclass，`Event.to_frame()` 直接产出可 JSON 序列化的字典。跨进程和将来跨 WebSocket 共用同一套形状，不用为传输再写一层 DTO。
4. 测试替身变简单：`LlmClient`、`TtsBackend`、`QueueLike` 都是 Protocol，测试实现一个类就能替换，不用 monkeypatch 模块级变量。
5. `contracts` 只 import 标准库，CI 里不装 GUI 依赖也能 import 它；这也挡住了循环 import：实现层可以引用契约，契约不能反过来引用实现层。

**代价**
- 多一跳：读实现时代码里全是 `from contracts import ...`，要跳一次才知道类型长什么样。
- `contracts` 是收口点：新增一个跨模块类型要改契约、改 [`reference.md`](reference.md)、改 `__init__.py` 的 `__all__`，比在本地随手定义一个类多几步。
- 有变成杂物间的风险：一旦把"只有一个调用方"的内部类型也搬进来，契约就不再是契约，改它的人会以为要同步改文档。
- `tts/base.py` 的 re-export 让同层代码少写一行 import，代价是同一个名字有两处可 import，读代码时容易误判定义位置。

**什么时候推翻**
某个类型只有一层用、又不跨进程，它就不该在 `contracts` 里，搬回实现层即可。如果一次功能改动只涉及界面显示、却要同时改 `contracts` 和三个实现层，说明这个类型的分层位置错了，先把它挪出去。远程客户端需要事件版本兼容时，给 `Event.to_frame()` 加版本字段，而不是取消契约层。

## 7. 单 agent 单循环，不引入 LangGraph 这类编排框架（尚未实施）

**背景**
M1 的 `runtime._run_turn()` 是一条直线：调 LLM 流式拿完整回复 → 关键词判情感 → 切句 → 逐句合成 → 派发播放。路线图 M3 才接 ReAct 工具调用。候选方案是 LangGraph / LlamaIndex / CrewAI 这类图编排框架，它们自带状态机、检查点、回调。

**决定**
保持一个 agent、一个手写循环，不引入编排框架。接工具时把 `_run_turn()` 改成循环：调模型 → 有 tool_calls 就执行 → 把结果塞回消息 → 再调模型，直到模型不再要工具。这条决定**尚未实施**：当前代码里没有工具调用，`LlmClient.stream()` 只产出文本增量，`runtime` 里也没有循环。

**理由**
1. 现在的状态机小到可以画在一张纸上：1 次 LLM、N 次 TTS、1 个取消标志。框架带来的状态模型、回调、序列化格式都要映射回现有 `Event`，映射层本身就是要维护的代码。
2. 这个作品要展示的是边界和契约，不是会用框架。手写循环里"取消检查点放哪、事件按什么顺序发、工具结果能不能合成语音"这些判断，正是面试要讲的东西；框架会把这些藏起来。
3. 现有事件形状够用：`Event` 的 `type` + `turn_id` + `to_frame()` 能直接承载 `agent.step` / `tool.call` / `tool.result`，基类不用改；在 `contracts` 里加新事件比引入一个框架轻。
4. 测试成本：手写循环用假 `LlmClient` 就能测分支；框架通常要跑它自己的运行时，CI 里更重，也更难 mock。

**代价**
- 工具调用的细节要自己写：参数解析、失败重试、最大轮数、循环中的取消，以及工具轮不能合成语音。
- 没有现成的检查点、恢复、可视化和并发分支；会话持久化和多 agent 得另做。
- 手写循环一旦出现"工具 A 的结果决定工具 B"的嵌套分支，代码会比图声明难读。
- 边流边合成得排在工具之后：工具轮没有可朗读的文本，两条改动叠在一起会互相干扰（[`architecture.md`](architecture.md) 第 5.3 节列了这个冲突）。

**什么时候推翻**
需要多 agent、并发分支、断点续跑、人工审批这类结构；或者单轮工具调用超过 3–4 个、循环状态多到需要可视化。那时再选框架，但 `contracts` 仍然是边界，界面和 TTS 不感知框架的存在。如果框架的运行时要求把事件模型改成它自己的形状，这笔账要重新算。
